# v2 战略设计

> v1 的问题：跳过了战略设计直接写战术代码，导致"限界上下文"退化成目录名。
> v2 从子域划分开始，每一步都说明**为什么这么切**、**切错的代价是什么**。

---

## 1. 子域划分：把好钢用在核心域

战略设计的第一步不是画聚合，是**判断哪块业务值得投入最好的设计**。

| 子域 | 类型 | 判断依据 | 设计投入 |
|---|---|---|---|
| **收单** | **核心域** | 支付成功率直接映射营收；资金一致性是生死线 | 最高：完整聚合建模、状态机、并发控制、领域事件 |
| **通道网关** | 支撑域 | 必须做，但业界有成熟范式（防腐层），无差异化 | 中：只做好抽象与双向翻译 |
| **退款** | 支撑域 | 业务必要，但逻辑相对收单简单 | 中：重点是跨上下文集成模式 |
| **对账** | 支撑域 | 兜底手段，跑批性质，无实时性要求 | 低：demo 阶段给骨架 |

### 为什么收单是核心域——量化论证

假设一个日交易额 1 亿的平台：

```
支付成功率提升 0.1%  →  日增收 10 万  →  年增收 3650 万
```

这 0.1% 从哪来？不是靠更炫的代码，靠的是**领域建模的精度**：

- 多通道重试（微信失败自动切支付宝）→ 挽回一部分失败
- 超时关单时机精准（关早了掉单，关晚了占用库存）→ 减少无效占用
- 幂等做到位 → 杜绝重复扣款引发的客诉与退款成本
- 状态机严谨 → 杜绝"支付失败却发了货"的资损

**这些都是领域逻辑，不是技术问题。** 这就是收单值得投入最高设计密度的原因。

反观对账：它重要，但做对了不会带来营收增长，做错了也只是延迟发现。所以它是支撑域——用成熟方案解决即可，不必投入核心域级别的设计。

> **v1 的错误**：把对账和收单放在同一个模块、同一层级建模，等于把 80% 的精力花在了只值 20% 的地方。

## 2. 限界上下文：按通用语言的边界切，不按数据表切

**限界上下文的本质**：一个**通用语言的边界**。在这个边界内，同一个词有唯一确定的含义。

这是最容易做错的一步。多数人按"业务功能模块"或"数据表"切上下文，结果切出来的是**模块**而不是**上下文**。

### 判断标准：同一个词，在不同上下文里含义是否不同？

| 词 | 收单上下文 | 退款上下文 | 对账上下文 | 通道网关上下文 |
|---|---|---|---|---|
| **支付单** | 正在推进状态的聚合根，有生命周期 | **已完成的支付事实**（不可变快照） | 一条待勾稽的账目记录 | 不存在这个概念 |
| **金额** | 待收金额，可能变化（部分支付） | 可退余额的约束来源 | 待比对的数值 | 通道报文里的字段 |
| **通道** | 一个枚举标识 | 不关心 | 账单来源 | **有行为的实体**：有签名算法、回调协议、能力矩阵 |
| **指令** | 不存在 | 不存在 | 不存在 | 核心概念：向通道发出的操作请求 |

**关键洞察**：退款上下文里的"支付单"和收单上下文里的"Payment 聚合"是**两个不同的概念**，只是恰好都叫"支付"。

- 收单眼里的 Payment：一个**活的对象**，会 CREATED → PAYING → SUCCESS，内部有不变量要守护
- 退款眼里的 Payment：一个**死的事实**，"这笔支付成功了，金额 100 元，通道是微信"——它是值对象，不可变

**v1 的错误**：`Refund.applyFor(Payment payment, ...)` 直接把收单上下文的活聚合传进了退款上下文。这不只是"跨聚合引用"的违规，更是**把两个上下文的模型强行统一**——迫使退款上下文理解收单上下文的整个状态机。

**v2 的做法**：退款上下文定义自己的值对象 `PaidFact`（支付事实），由收单上下文通过**发布语言**投递过来。退款上下文永远不 import 收单上下文的 Payment。

### 上下文清单

```
┌─────────────────────────────────────────────────────────────┐
│                     收单上下文（核心域）                       │
│  通用语言：支付单、支付指令、收银凭证、支付尝试、预下单、关单      │
│  聚合根：Payment          实体：PaymentAttempt                │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│                     退款上下文（支撑域）                       │
│  通用语言：退款申请、退款单、退款渠道、支付事实（外部概念）        │
│  聚合根：Refund           值对象：PaidFact                    │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│                     对账上下文（支撑域）                       │
│  通用语言：对账批次、渠道账单、勾稽、差异、长短款                │
│  聚合根：ReconciliationBatch   值对象：BillItem、Discrepancy   │
└─────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────┐
│                 通道网关上下文（支撑域 · 防腐层）                │
│  通用语言：通道指令、通道回执、异步通知、通道能力、签名            │
│  聚合根：ChannelInstruction  值对象：ChannelCapability         │
└─────────────────────────────────────────────────────────────┘
```

## 3. 上下文映射：定义集成模式

上下文之间怎么通信，是战略设计里最需要显式决策的部分。DDD 给出九种模式，本项目用到四种：

```
                          ┌──────────────┐
                          │   商户系统     │
                          └──────┬───────┘
                                 │ 开放主机服务（OHS）
                                 ▼
     ┌──────────────────────────────────────────────────────┐
     │                    收单上下文                          │
     │                    （核心域）                          │
     └────┬──────────────────┬──────────────────┬───────────┘
          │                  │                  │
     发布语言           防腐层（入站）        防腐层（出站）
   PaymentSucceeded     账单数据接入        支付指令下发
          │                  │                  │
          ▼                  ▼                  ▼
   ┌────────────┐   ┌──────────────┐   ┌──────────────────┐
   │ 退款上下文   │   │  对账上下文    │   │  通道网关上下文     │
   │（下游）      │   │  （下游）      │   │  （防腐层）        │
   └─────┬──────┘   └──────────────┘   └──────────────────┘
         │                                       │
         └──────────── 防腐层 ──────────────────►│
               退款指令下发                       │
                                                 ▼
                                        微信 v3 / Stripe
```

| 上游 → 下游 | 模式 | 契约 | 为什么选这个模式 |
|---|---|---|---|
| 收单 → 退款 | **发布语言（Published Language）** | `PaymentSucceeded` 集成事件 v1 | 两个上下文都要长期演进，共享模型会导致互相锁死。发布语言是版本化的、只读的事实 |
| 收单 → 对账 | **防腐层** | 对账侧定义 `BillItem`，从收单数据翻译 | 对账不应受收单模型变化影响 |
| 收单 → 通道网关 | **防腐层（出站）** | `ChannelCommand` | 通道协议千差万别，必须隔离 |
| 通道网关 → 收单 | **防腐层（入站）** | `ChannelReceipt`（通道回执） | 通道报文翻译为领域语言后才能进入收单 |
| 退款 → 通道网关 | **防腐层** | `ChannelCommand` | 同上 |
| 全部 | **共享内核（Shared Kernel）** | 仅 `Money` / `DomainEvent` / `ChannelCode` | 极小的公共集，且**只读** |

### 共享内核必须是极小的

共享内核是上下文间的"共同财产"，任何一方的修改都会影响另一方。所以它必须**小到不能再小**：

```java
// shared-kernel 只允许这些：
Money                 // 金额+币种，任何涉及钱的系统都要用
DomainEvent           // 事件基类（eventId/occurredAt/aggregateId）
IntegrationEvent      // 集成事件标记接口
ChannelCode           // 通道标识枚举（跨上下文通信需要）
```

**绝不允许**：`Payment`、`Refund`、`Merchant` 进入共享内核——一旦进去，上下文边界就名存实亡了。

> **v1 的错误**：四个"上下文"共享同一个 `com.zx.payment.domain` 包根，等于把整个领域模型都变成了共享内核。

## 4. 发布语言契约

收单 → 退款的集成，是本项目唯一的核心跨域流程。契约必须**版本化、只读、不含领域行为**。

### PaymentSucceeded v1

```java
/**
 * 集成事件（发布语言）：支付成功事实。
 *
 * 契约规则：
 *  1. 只读——下游不得修改，只能读取；
 *  2. 版本化——字段只能增不能改，破坏性变更要升 v2；
 *  3. 自包含——下游无需回调上游即可完成业务（含金额、通道、时间）；
 *  4. 不含领域行为——它不是 Payment 聚合，只是一份事实记录。
 */
public record PaymentSucceededV1(
        String eventId,
        Instant occurredAt,
        String paymentId,        // 收单上下文的聚合标识（下游仅作引用，不可解释其内部结构）
        String merchantId,
        String merchantOrderNo,
        long amountMinor,        // 最小货币单位，避免精度歧义
        String currency,
        String channelCode,
        String channelTradeNo,
        Instant paidAt
) implements IntegrationEvent {

    /** 便利方法：还原为 Money。注意这只是【读取】，不是翻译——不引入任何下游概念。 */
    public Money paidAmount() {
        return Money.ofMinor(paidAmountMinor, CurrencyCode.of(currency));
    }
}
```

**为什么这里没有 `toPaidFact()`**：我最初的设计稿里写了这个方法，那是错的。

`PaidFact` 属于**退款上下文**。如果在共享内核的契约里提供 `toPaidFact()`，共享内核就必须 import 退款上下文的类型——依赖方向从"上游 → 下游"倒挂成"上游依赖下游"，上下文边界当场失效。

正确做法：**契约保持纯数据，翻译器放在下游自己的防腐层**。

```java
// refund-application/acl/PaymentSucceededTranslator.java（下游，退款上下文）
public static PaidFact toPaidFact(PaymentSucceededV1 event) {
    return new PaidFact(event.paymentId(), ..., event.paidAmount(), event.channel(), ...);
}
```

这符合防腐层的核心原则——**谁需要，谁翻译**。收单上下文永远不知道退款上下文长什么样。

## 5. 物理架构：模块边界即架构约束

战略设计如果只停留在文档，等于没做。**必须让编译器能强制执行边界**。

```
payment-ddd-v2/
├── shared-kernel/                    # 极小共享内核（Money / 事件基类 / ChannelCode）
│
├── acquisition-context/              # 收单上下文（核心域）
│   ├── acquisition-domain/           #   ┐ 领域层 + 应用层
│   └── acquisition-application/      #   ┘ 外部只能通过 application 访问
│
├── refund-context/                   # 退款上下文
│   ├── refund-domain/
│   └── refund-application/
│
├── reconciliation-context/           # 对账上下文
│   └── reconciliation-domain/
│
├── channel-gateway-context/          # 通道网关上下文（防腐层）
│   ├── channel-domain/               #   端口与领域模型
│   └── channel-infrastructure/       #   微信 v3 / Stripe 适配器
│
└── bootstrap/                        # 启动与 REST，唯一允许依赖所有上下文的模块
```

### 依赖规则（可用 Maven enforcer 强制检查）

| 模块 | 允许依赖 | 禁止依赖 |
|---|---|---|
| `shared-kernel` | 无（仅 JDK） | 任何业务模块 |
| `acquisition-domain` | `shared-kernel` | 其他上下文 |
| `acquisition-application` | `acquisition-domain`、`shared-kernel` | 其他上下文的 domain |
| `refund-domain` | `shared-kernel` | **`acquisition-*`**（这是 v1 的核心错误） |
| `refund-application` | `refund-domain`、`shared-kernel` | `acquisition-domain` |
| `channel-gateway-context` | `shared-kernel` | 任何业务上下文 |
| `bootstrap` | 所有 | —— |

**关键约束**：`refund-domain` 的依赖里**绝不允许出现 `acquisition-domain`**。这不是约定，是**编译期强制**——想违规都违规不了。

跨上下文的通信只能走两条路：

1. **集成事件**（异步）：通过 `shared-kernel` 里定义的 `IntegrationEvent` 契约
2. **应用层编排**（同步）：在 `bootstrap` 或独立的应用服务里组合两个上下文的 application 服务，**但传入传出的是 DTO/值对象，不是领域对象**

### 为什么上下文还要再分 domain / application 两层

不是为了凑层次。原因是**对外暴露的边界**：

- `xxx-domain`：上下文的核心，只有上下文内部能用
- `xxx-application`：对外接口层，定义"这个上下文能为你做什么"

外部上下文只能看到 application，看不到 domain 里的聚合内部。这样即使把 Payment 聚合重构了，只要 application 接口不变，其他上下文零感知。

## 6. 与 v1 的对照

| 维度 | v1 | v2 |
|---|---|---|
| 起点 | 直接写聚合 | 子域划分 → 上下文 → 映射 → 契约 → 聚合 |
| 上下文边界 | 包目录，可自由 import | Maven 模块，编译期强制 |
| 共享内核 | 整个 `com.zx.payment.domain` | 仅 Money / 事件基类 / ChannelCode |
| 跨域通信 | `Refund.applyFor(Payment payment, ...)` 对象直传 | 发布语言 `PaymentSucceededV1` + 下游翻译 |
| 跨域一致性 | 单事务强一致 | 领域事件 + Outbox 最终一致 |
| 通道数量 | 8 个（40% 代码量，收益低） | 2 个（微信 v3 + Stripe，覆盖两种典型协议） |
| 目标 | 跑通全流程 | 架构正确性可评审 |
