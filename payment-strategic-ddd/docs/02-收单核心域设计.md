# 收单核心域设计

> 这是 v2 的投入重点（核心域）。每个决策都给出：**有啥选择 → 选了哪个 → 为什么 → 什么情况下该改选**。

---

## 1. 状态机：比 v1 多了两个真实状态

```
                    ┌──────────┐
                    │  CREATED │
                    └────┬─────┘
                         │ 首次下单
                         ▼
          ┌─────────► ┌────────┐ ◄─────────┐
          │ 换通道重试  │ PAYING │  继续支付   │
          │           └───┬────┘           │
          │      ┌────────┼────────┐       │
     失败 │      ▼        ▼        ▼       │
          │ ┌────────┐ ┌───────┐ ┌─────────┴─┐
          └─│ FAILED │ │SUCCESS│ │  PARTIAL   │
            └────────┘ └───────┘ └─────┬─────┘
                                       │ 补齐
                                       ▼
                                     SUCCESS

     CREATED/PAYING/PARTIAL/FAILED ──关单──► CLOSED
```

### 决策一：加 PARTIAL（部分支付）

v1 只有 SUCCESS/FAILED，隐含假设"一次付清"。真实业务不成立：

- 组合支付（余额 ¥4 + 银行卡 ¥6）
- 分次付款（先付定金）
- 通道部分成功（少见但存在）

**代价**：状态机复杂度上升（PARTIAL → 三条出边），且带来一个容易漏的点——

> **PARTIAL 关单必须自动退款**。用户付了一半被关单，钱得退回去。
> 所以 `PaymentClosedEvent` 携带 `receivedAmount` 字段，下游据此触发退款。
> 这个字段漏了就是资损，测试里专门有一条用例盯着它（`部分支付后关单需退款`）。

### 决策二：FAILED 不是终态，允许换通道重试

v1 把 FAILED 当终态，等于放弃了支付成功率的优化空间。真实数据：

```
某支付平台通道失败原因分布：
  余额不足 / 限额  .........  42%   ← 换通道/换卡可挽回
  风控拒绝        .........  18%   ← 不可重试，重试只会再拒
  网络超时        .........  25%   ← 可重试（但要防重复扣款）
  账户异常        .........  15%   ← 不可重试
```

所以 `confirmAttemptFailure(..., retriable)` 多了一个参数——**由通道告诉你能不能重试**，而不是领域层拍脑袋。

- `retriable=true` 且未达次数上限 → FAILED，等应用层换通道
- `retriable=false` → FAILED + 发 `PaymentFailedEvent`

**MAX_ATTEMPTS = 3** 的考量：太少浪费可挽回的单，太多会打爆通道接口（渠道方通常会限流甚至降权）。

### 不变量：同一时刻只有一个 active attempt

```java
PaymentAttempt active = activeAttempt();
if (active != null) {
    throw new IllegalStateException("已存在进行中的尝试，不可并发下单");
}
```

这条拦的是**重复扣款**——用户手抖点两下、前端重复提交、网络重试，都可能导致同一笔单下两次单。这是资损级防线。

## 2. 聚合边界：什么该进聚合，什么不该

这是 v1 踩过的坑，也是聚合设计最实用的判据。

> **判据**：删掉这个对象，会不会破坏某条业务不变量？
> 会 → 必须在聚合内（强一致守护）
> 不会 → 不该进（放进去只是拖累性能和语义）

| 对象 | 在聚合内？ | 判据检验 |
|---|---|---|
| `PaymentAttempt` | ✅ 是 | 删掉它 → 无法保证"不超收"、"不并发下单" → **必须进** |
| 通道调用流水（HTTP 报文） | ❌ 否 | 删掉 → 业务照常跑，只是不好排查 → **不该进** |
| `Merchant`（商户） | ❌ 否 | 商户有自己的生命周期，支付单不需要强一致地改商户 → **不该进**（只存 merchantId） |

**v1 的错误**恰好是反的：把技术流水（`PaymentTransaction`）放进了聚合，而真正该在聚合内的 attempt 反而没有（v1 一个支付单绑死一个通道，不存在多次尝试的概念）。

后果很实际：
```java
// v1：每次加载支付单都拖出全部历史报文
payment.getTransactions()  // 重试 5 次就有 5 条，每条含完整 JSON 报文
```
高频查询场景下这是纯粹的性能浪费。技术流水应该走独立的读模型/日志系统。

## 3. 并发控制：乐观锁 vs 分布式锁

### 场景

同一笔支付单的状态推进可能同时发生：
- 通道异步回调到达
- 定时任务主动查单补偿
- 商户主动关单

### 三个方案对比

| 方案 | 机制 | 平均开销 | 冲突时代价 | 复杂度 |
|---|---|---|---|---|
| **乐观锁（选它）** | `version` 字段 CAS | 0 | 重试一次 ~20ms | 低 |
| 分布式锁 | Redis SETNX | +0.5ms/次 | 等待锁释放 | 高（锁超时、续约、死锁） |
| DB 行锁 | `SELECT FOR UPDATE` | 连接占用 | 阻塞 | 中（死锁风险） |

### 量化决策

单笔支付的状态推进是**稀疏事件**——下单、回调、查单之间通常间隔秒级。真正撞进同一 10ms 窗口的概率极低。

```
假设冲突概率 p = 0.1%（已经很保守）

乐观锁期望开销 = p × 重试成本 = 0.001 × 20ms  = 0.02ms
分布式锁开销   = 1.0 × 加锁成本 = 1.0 × 0.5ms  = 0.5ms

乐观锁快 25 倍
```

**结论**：为 0.1% 的冲突，让 100% 的请求都付加锁代价，不划算。

### 但光有状态机幂等还不够——ABA 问题

有人会说："我状态机已经检查了 `status == SUCCESS 就返回 false`，还要乐观锁干嘛？"

因为状态机挡不住这个序列：

```
T1 读到 PAYING，准备推进 SUCCESS
T2 推进到 SUCCESS
T3 商户取消，状态变 CLOSED
T1 的写入落地 → 状态被改回 SUCCESS    ← 已关闭的单"诈尸"成支付成功
```

状态机检查的是"当前状态是否允许本次迁移"，**检查与写入之间存在时间差**。乐观锁把这个时间差消灭掉：

```sql
UPDATE t_payment SET ..., version = version + 1
WHERE payment_id = ? AND version = ?
-- 影响行数 0 → 抛 OptimisticConcurrencyException
```

T1 提交时 version 已被 T2/T3 改过，更新失败。**状态机幂等 + 乐观锁，两者缺一不可。**

### 什么时候该改用分布式锁

- **批量操作**：批量关单、批量退款，同一批数据冲突概率高
- **跨聚合操作**：涉及多个聚合的原子变更，乐观锁管不过来
- **单笔支付的状态推进**：就是现在这个场景，乐观锁更优

## 4. 幂等：三个层次，防的是三种不同的事

| 层次 | 机制 | 防的是什么 |
|---|---|---|
| **创建幂等** | `merchantOrderNo` 唯一索引，命中即返回 | 商户网络重试、前端重复提交 |
| **状态幂等** | `succeed()`/`fail()` 终态返回 false | 通道重复回调（应答格式错会导致重发，Antom 24h 内最多 8 次） |
| **尝试幂等** | `PaymentAttempt.succeed()` 幂等 | 同一 attempt 的重复成功通知 |

关键设计：**幂等方法返回 boolean**，让调用方知道"这次到底有没有真的推进"。

```java
boolean changed = payment.confirmAttemptSuccess(...);
if (changed) {
    // 真的推进了，才需要发事件、记日志
}
```

v1 里 `succeed()` 返回 boolean 是对的，这个设计在 v2 保留了。

## 5. 超时关单：领域事件驱动，不是轮询全部

```
PaymentCreatedEvent
    ↓ 订阅
注册延迟任务（延迟 = expireTime - now）
    ↓ 到期
触发 close 命令 → payment.close("超时未付清")
    ↓
PaymentClosedEvent（携带 receivedAmount）
    ↓
若 receivedAmount > 0 → 触发自动退款
```

**为什么用事件驱动而不是定时扫全表**：
- `PaymentCreatedEvent` 在创建时就带上了 `expireTime`，订阅方直接据此注册延迟任务，精度到秒
- 定时扫全表的问题是：扫描间隔决定精度（5 分钟扫一次 → 平均延迟 2.5 分钟关单），且数据量增长后扫描变慢

**但要有兜底**：延迟任务可能丢（进程重启、MQ 故障）。所以还需要一个低频的补偿扫描（`findExpiredCandidates`），比如每 10 分钟扫一次未终态且已过期的单。事件驱动负责精度，定时扫描负责可靠性。

关单本身的幂等性保证了两者并发也安全：`close()` 遇到终态返回 false。

## 6. 事件发布：Outbox 模式（这是 v1 最严重的 bug）

### v1 的做法与后果

```java
@Transactional
public void close(String paymentId, String reason) {
    payment.close(reason);
    paymentRepository.save(payment);
    publishDrained(payment);   // ← 同步发布，还在事务里！
}
```

Spring 的 `ApplicationEventPublisher` 默认**同步、同线程、同事务**。这意味着：

```
事务开始
  ↓
状态改为 CLOSED
  ↓
发布 PaymentClosedEvent → 订阅方执行 → 发短信、通知商户、退库存
  ↓
数据库异常，事务回滚
  ↓
【状态回到 PAYING，但短信已经发出去了】
```

在支付系统里，这类 bug 的后果是：用户收到"支付成功"但订单其实没成功，或者反过来。**文档里我写的是"事务提交后发布"，代码做的却是事务内同步发布——文档与实现不符，这是最糟的一种错误。**

### v2 的做法：Outbox

```
事务内：
  1. 改聚合状态
  2. 把领域事件写入 outbox 表（同一事务，同生共死）
  3. 提交

事务外（独立线程/进程）：
  4. 轮询 outbox 表，取出未投递事件
  5. 投递到 MQ
  6. 标记已投递（消费端需自己做幂等）
```

**核心保证**：事件与状态变更在同一个事务里，要么都成要么都不成。投递是异步的，失败了重试，不会丢。

**代价**：投递有延迟（通常 < 1s），且消费端必须幂等（因为可能重复投递）。这是分布式系统的标准取舍——用最终一致换可靠性。

## 7. 与 v1 的逐条对照

| 维度 | v1 | v2 | 影响 |
|---|---|---|---|
| 状态机 | 5 态，FAILED 终态 | 6 态，加 PARTIAL，FAILED 可重试 | 支持部分支付与换通道重试 |
| 聚合边界 | 技术流水在内，无 attempt | attempt 在内，流水在外 | 语义清晰 + 加载性能 |
| 并发控制 | 无（仅状态机检查） | 状态机 + 乐观锁 | 杜绝 ABA 导致的诈尸 |
| 幂等 | 2 层 | 3 层（+attempt 层） | 覆盖重复成功通知 |
| 事件发布 | 事务内同步（bug） | Outbox 异步 | 杜绝"通知发了但事务回滚" |
| 关单 | 需外部触发 | 事件驱动 + 定时兜底 | 精度到秒，且可靠 |
| 退款耦合 | `applyFor(Payment payment)` | `apply(PaidFact, ...)` | 上下文解耦 |
