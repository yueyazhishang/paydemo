# DDD 在跨境支付系统中的应用研究

> 本文讨论的是**领域建模方法论在特定业务域的应用**，配套代码只是论证的载体，不追求可运行。
> 核心问题只有一个：**跨境支付相比国内支付，多出来的那部分复杂度到底是什么？DDD 的哪些工具能精确地吃掉它，哪些不能？**

---

## 摘要

跨境支付值得用 DDD，不是因为它"很复杂"，而是因为它的复杂度有明确的结构：**多主语、长链路、强合规、弱一致**。这四点恰好分别对应 DDD 的四个工具：限界上下文、领域事件、上下文隔离、聚合不变量。

但 DDD 在跨境支付上也有明确的**能力边界**：它解决不了汇率定价模型的选择、解决不了通道谈判、解决不了各国牌照的获取路径。把 DDD 当成万能钥匙，会做出一个"包结构很漂亮但业务跑不通"的系统。

**本文的核心观点**：在跨境支付中，DDD 最大的价值不在战术设计（聚合/值对象这些），而在**战略设计**——尤其是"核心域/支撑域/通用域的判定"和"上下文映射模式的选择"。前者决定你把最优秀的人放在哪里，后者决定系统十年后还能不能改。

---

## 一、为什么跨境支付是 DDD 的绝佳试验场

### 1.1 复杂度来自哪里：从技术问题到领域问题

国内支付系统的复杂度主要是**技术复杂度**：高并发、低延迟、强一致。这些有成熟解法（分库分表、缓存、分布式事务），且解法与业务无关。

跨境支付叠加的是**领域复杂度**：

| 维度 | 国内支付 | 跨境支付 | 复杂度类型 |
|---|---|---|---|
| 币种 | 1 种（CNY） | 100+ 种 | 领域 |
| 汇率 | 不存在 | 报价/锁定/汇损/重估 | 领域 |
| 支付方式 | 3~5 种（微信/支付宝/银联） | 300+ 种（APM 长尾） | 领域 |
| 通道 | 3~8 个 | 数十个，跨大区 | 领域 |
| 合规 | 相对统一 | 各国独立：KYC/AML/制裁/PSD2/数据驻留 | 领域 + 组织 |
| 拒付 | 无此概念（走投诉） | chargeback 全流程，有举证时限 | 领域 |
| 结算周期 | T+1 为主 | T+1 ~ T+7，随市场/通道变化 | 领域 |
| 日切 | 统一（北京时间） | 各市场独立 + 各自节假日 | 领域 |
| 税务 | 增值税为主 | VAT/GST/预提税/跨境服务费税 | 领域 |
| 峰值 QPS | 极高（大促百万级） | 相对低（万级） | **技术** |

**关键观察**：最后一行的技术复杂度，跨境反而**更低**。这意味着——

> 跨境支付系统的难点不是"扛住流量"，而是"把业务说清楚"。
> 这恰恰是 DDD 的主场。

反过来说，如果一个团队拿做国内支付的思路做跨境（先堆性能、后理业务），大概率会在合规改造和通道扩展上反复返工。

### 1.2 复杂度增量：一个量化视角

假设一个国内支付系统的领域概念数量约为 N。接入跨境后：

| 概念类别 | 国内 | 跨境增量 | 说明 |
|---|---|---|---|
| 币种与汇率 | ~2 | +15 | Money / Currency / ExchangeRate / RateQuote / RateLock / FxLoss / Revaluation... |
| 支付方式 | ~5 | +50（按需接入） | 每个 APM 是一组独立概念 |
| 通道能力维度 | ~8 | +12 | 新增：制裁筛查、SCA/3DS、拒付、数据驻留、本地清算 |
| 合规对象 | ~3 | +20 | KYB / 受益所有人 / 制裁名单 / PEP / 高风险国家... |
| 资金流状态 | ~8 | +15 | 汇出/汇入/在途/结汇/待申报... |
| 领域事件 | ~10 | +25 | 跨境链路长，需要更多事件分段推进 |

**总量约 3~5 倍的概念膨胀**，而且这些概念之间不是平铺的——它们有明显的**聚类结构**（币种相关、合规相关、通道相关各自成团）。

**这个聚类结构，就是限界上下文划分的天然依据。**

### 1.3 DDD 能解决什么，不能解决什么

先把边界划清楚，避免过度设计：

**DDD 能解决的：**
- 概念膨胀导致的认知负担 → 限界上下文切分
- 通道差异导致的抽象泄漏 → 防腐层
- 长链路导致的一致性问题 → 领域事件 + Saga
- 业务规则散落导致的不可测 → 聚合内聚不变量
- 团队分工与系统演进 → 上下文映射

**DDD 解决不了的：**
- 汇率定价策略（加点多少、谁承担汇损）—— 这是商务决策
- 通道费率谈判与选择 —— 商务 + 数据分析
- 各市场牌照获取路径 —— 法务 + 合规策略
- 通道自身的可用性 —— 只能靠工程手段缓解，不能靠建模消除

**误用 DDD 的典型症状**：为了"领域纯洁性"拒绝使用成熟中间件，自己造一套"领域友好"的消息队列 / 定时任务 / 配置中心。这是把 DDD 当宗教，不是当工具。

## 二、战略设计：限界上下文怎么切

### 2.1 上下文全景

```
                            ┌──────────────┐
                            │   商户上下文   │  Merchant
                            │ KYB/资质/费率  │
                            └──────┬───────┘
                                   │ 商户资质就绪
    ┌──────────────────────────────┼──────────────────────────────┐
    │                              ↓                              │

│  合规上下文  │◀─────────│   收单上下文       │──────────→│   外汇上下文    │
```

### 2.2 核心域 / 支撑域 / 通用域：最被低估的 DDD 工具

这是 DDD 战略设计里**最实用、也最常被跳过**的一步。它的价值不是分类本身，而是**决定资源投放**。

| 上下文 | 域类型 | 判定理由 | 资源策略 |
|---|---|---|---|
| **通道路由与编排** | **核心域** | 直接决定成功率与成本，是支付平台的利润来源。路由策略的优化空间几乎无限 | 自研，配置最优秀的人 |
| **收单** | **核心域** | 主链路，所有业务的起点。但模型相对标准化 | 自研，追求稳定 |
| **外汇（FX）** | **核心域**（跨境特有） | 汇损控制是跨境支付的核心利润点之一。汇率时点选择、锁汇策略直接影响毛利 | 自研或深度定制 |
| **结算** | **核心域** | 资金出去的最后一环，出错就是资损 | 自研 |
| **争议/拒付** | **支撑域** | 重要但标准化，有成熟的 SaaS（如 Chargeback 管理平台） | 可外采，但要自持数据 |
| **合规** | **支撑域**（但高风险） | 规则变化极快，但业务模式成熟 | 优先外采专业服务，自研编排层 |
| **账务** | **支撑域** | 复式记账是成熟领域，规则稳定 | 外采或基于成熟方案定制 |
| **对账** | **支撑域** | 逻辑固定，主要是工程量大 | 自研，但追求的是工程效率而非建模 |
| **通道适配** | **通用域**（但需自研） | 每个通道都一样地"脏"，没有差异化价值 | 标准化模板 + 快速接入 |
| **通知/消息** | **通用域** | 完全标准化 | 直接用中间件 |

**一个反直觉的判断**：通道适配代码量最大（本工程 9 个适配器占了很大篇幅），但它是**通用域**。

> 代码量 ≠ 领域价值。
> 通道适配的本质是"把别人的脏模型翻译成自己的干净模型"，它是**成本**，不是**竞争力**。
> 真正的竞争力在通道路由：同样接 9 个通道，能否把每一笔交易路由到"成功率最高 + 成本最低"的那个。

这也解释了为什么本工程把通道适配做成高度标准化的模板（能力矩阵 + 抽象基类），而把路由策略做成可插拔的 `RouteStrategy`。

### 2.3 上下文映射：集成模式的选择

上下文之间怎么协作，DDD 给了几种标准模式。选错模式的代价，往往几年后才显现。

#### ① 防腐层（Anti-Corruption Layer）：通道适配

**这是本工程最核心的范式。**

通道的外部模型（微信的 XML/JSON、Worldpay 的 XML、Stripe 的 PaymentIntent）会持续变化，且变化不受我们控制。如果让它渗透进领域模型，每次通道升级都要改核心代码。

**防腐层的三层职责**（很多实现只做了第一层）：

| 层次 | 职责 | 本工程实现 |
|---|---|---|
| **协议转换** | XML ↔ JSON ↔ form | 各适配器的 `parseNotification` |
| **语义翻译** | 通道状态 → 领域状态 | `mapStatus()`、`ChannelResultStatus` |
| **能力声明** | 通道能做什么 | `ChannelCapability` |

**第三层最容易被忽略，也最重要。** 只做字段映射、不做能力声明，上层就必然退化成 `if (channel == WECHAT)`，防腐层形同虚设。

#### ② 共享内核（Shared Kernel）：Money

Money 被所有上下文使用，且必须严格一致——如果收单上下文的 Money 保留 2 位小数、外汇上下文保留 4 位，跨上下文传递时就会静默丢精度。

共享内核的代价是：**任何修改都要所有使用方同意**。这决定了 Money 必须是高度稳定、不可变、无业务逻辑的。

本工程把 Money 放在 `payment-shared-kernel`，且它**零外部依赖**——这不是洁癖，是为了让共享内核无法被任何一方单方面污染。

#### ③ 客户方-供应方（Customer-Supplier）：收单 → 结算

收单是供应方（产出 PaymentSucceeded 事件），结算是客户方（消费事件）。供应方必须考虑客户方的需求，但客户方不能反过来要求供应方改模型。

实践中体现为：**事件契约要版本化，且向后兼容**。新增字段可以，删改字段不行。

#### ④ 遵奉者（Conformist）：合规服务

如果合规能力是外采的（如制裁名单筛查服务），且它的模型无法协商，那就只能遵从它的模型——但在自己这一侧加一层薄薄的防腐，避免外部模型直接成为领域对象。

#### ⑤ 分离方式（Separate Ways）

某些能力如果集成成本高于收益，就不如各自实现。例如：各业务线的通知模板，与其做统一平台，不如各写各的。

### 2.4 上下文之间的协作：为什么是事件，不是调用

跨境链路的两个特点决定了必须用事件：

1. **长**：一笔跨境支付可能跨越 T+0 到 T+7，中间涉及收单、汇率、清算、结算、申报。同步调用链无法表达这种时间跨度。
2. **异构参与者多**：收单、结算、账务、风控、合规、通知——这些系统的可用性、响应时间、部署节奏完全不同。同步调用会让最慢的那个拖垮全链路。

事件驱动让"支付成功"这个事实被**宣布**，而不是被**推送**。谁关心谁订阅，支付主链路不感知下游存在。

## 三、跨境特有的领域深水区

这一节是本文的重心。以下五个领域，是国内支付完全没有或极度弱化的。

### 3.1 多币种与汇率：值对象设计的深水区

#### Money 的三种建模方案

| 方案 | 优点 | 致命问题 |
|---|---|---|
| `BigDecimal amount` + `String currency` | 简单直观 | 浮点污染入口（只要有人写了 `new BigDecimal(0.1)`）；跨币种相加不报错 |
| `long minorUnits` + `Currency` | 精度可控、通道对齐 | 展示层需转换；必须自己处理币种指数 |
| `Money` 值对象 + 显式汇率对象 | 类型安全，跨币种运算必须显式 | 学习成本，代码略啰嗦 |

**本工程选第二种（Money 内部存 long，币种自带指数）**，理由见架构文档。这里补充跨境视角的关键点：

**币种指数是数据，不是常量。** 三种货币就足以击穿"统一乘 100"的假设：

| 币种 | 指数 | 100 单位货币的最小单位值 | 按"乘100"的错误结果 |
|---|---|---|---|
| CNY | 2 | 10000 | 10000 ✓ |
| JPY | 0 | 100 | 10000 ✗（100 倍长款） |
| KWD | 3 | 100000 | 10000 ✗（10 倍资损） |

在跨境场景下这不再是一个边界 case——JPY 是主要货币之一，KWD/BHD/OMR 等三位小数币种在中东市场很常见。

#### 汇率不是数字，是有生命周期的实体

新手最常见的错误：`Money convert(Money from, BigDecimal rate, Currency to)`。

这个签名隐含了三个错误假设：

1. **汇率是无时间的常量** → 实际汇率随时变，报价有时效
2. **汇率是无来源的** → 谁报的价？加点多少？可追溯吗？
3. **转换是无损的** → 汇损归谁？这个业务问题被技术签名吃掉了

**正确的建模**：

```
RateQuote（汇率报价）
  ├── 买入价/卖出价/中间价
  ├── 报价来源（路透/通道/银行）
  ├── 报价时间 + 失效时间     ← 有时效！
  └── 加点（markup）明细

RateLock（汇率锁定）
  ├── 关联的 RateQuote
  ├── 锁定的汇率值
  ├── 锁定期限               ← 酒店/机票场景可能锁 24 小时
  └── 锁定成本

FxLoss（汇损）
  ├── 预期汇率 vs 实际汇率
  ├── 损失金额
  └── 承担方（平台/商户/用户）  ← 这是商务决策，必须在模型里显式表达
```

**"汇损承担方"这一项尤其关键。** 它不是技术细节，而是商业模式的一部分：
- 平台承担 → 汇率风险在平台，需要外汇对冲能力
- 商户承担 → 商户看到的是浮动结算额，需要提前告知
- 用户承担 → 用户支付时看到的是估算金额，实际扣款可能不同（合规风险）

把这个决策藏在一行 `multiply(rate)` 里，迟早会在对账时炸出来。

#### 币种转换的时点选择

三个可选时点，各有业务含义：

| 时点 | 汇率风险 | 用户预期 | 典型场景 |
|---|---|---|---|
| 下单时锁定 | 平台承担 | 显示即所得 | 电商、酒店 |
| 支付时锁定 | 平台承担（窗口短） | 基本一致 | 大部分场景 |
| 结算时锁定 | 商户承担 | 商户看到的结算额浮动 | B2B、平台型 |

**这个选择必须体现在领域模型里**，因为它决定了 RateLock 的生命周期和 FxLoss 的归属。

### 3.2 合规域：为什么必须独立成上下文

合规是跨境支付中最"烦"的部分，也最容易被做成散落在各处的 if-else。

#### 为什么它必须独立

| 理由 | 说明 |
|---|---|
| **变化频率不同** | 支付业务规则以季度为单位演进；合规规则可能因为一纸文件在一周内变化。变化的**节奏**不同，就应该隔离 |
| **变化来源不同** | 业务规则来自产品；合规规则来自监管机构、卡组织、通道。来源不同的东西不该共享模型 |
| **失败语义不同** | 业务失败是"这次没成"；合规失败可能是"这个主体不能服务"，需要进入受限名单并留痕 |
| **审计要求不同** | 合规决策必须可追溯：什么时间、依据哪条规则、由哪个版本的规则引擎做出。这要求独立的事件日志 |
| **性能模型不同** | 制裁名单筛查是一次重 IO 操作（可能调用外部服务），与支付主链路的低延迟要求冲突 |

#### 合规域的核心概念

```
ComplianceContext
  ├── Subject（主体：个人/企业）
  │     ├── KYC 等级（决定交易限额）
  │     ├── 受益所有人（UBO，企业必查）
  │     └── 风险评级
  ├── Screening（筛查）
  │     ├── 制裁名单（OFAC / EU / UN / 各国本地）
  │     ├── PEP（政治公众人物）
  │     └── 负面新闻
  ├── SCA（强客户认证，PSD2 要求）
  │     ├── 豁免判定（低风险/小额/白名单商户）
  │     └── 3DS 挑战流程
  └── DataResidency（数据驻留）
        ├── 数据分类（PII / 支付数据 / 卡数据）
        └── 存储地约束（GDPR / 中国数据出境 / 印度 RBI 本地化要求）
```

**数据驻留这一项常被忽略**：印度 RBI 要求支付数据必须本地存储，中国的数据出境有安全评估要求，欧盟 GDPR 对个人数据传输有限制。这不是"加个配置项"能解决的——它会影响表结构设计、部署架构、甚至上下文的物理边界（某些数据根本不能出境）。

#### 合规与收单的协作方式

```
支付请求 → 收单上下文 → 发 ComplianceRequested 事件
                          ↓
                       合规上下文（异步筛查）
                          ↓ ComplianceResult(通过/拒绝/需人工)
                       收单上下文继续或终止
```

**关键设计：合规是异步的。** 同步筛查会让支付链路的延迟被合规服务拖垮（制裁筛查可能耗时数百毫秒甚至调用外部服务）。

但异步带来一个问题：**先放行后筛查的风险**。折中方案是分层：
- 轻量同步筛查（本地名单缓存、规则引擎）：拦截明显违规，毫秒级
- 重量异步筛查（外部服务、人工复核）：异步进行，可对已支付订单发起冻结/退款

这在领域上体现为订单需要一个 **"待合规放行"的中间状态**，以及对应的**事后撤销能力**。

### 3.3 长事务与 Saga：跨境支付的默认一致性模型

#### 为什么跨境支付天然是最终一致

一笔跨境支付的完整链路：

```
用户下单 → 收单 → 汇率锁定 → 合规筛查 → 通道扣款 → 通道清算（T+1~T+7）
       → 资金归集 → 结汇 → 商户结算 → 申报
```

这条链路跨越**多个组织**（我方、通道、收单行、清算组织、银行），**多个时区**，**数天时间**。任何"分布式事务"幻想在这里都不成立。

**结论：跨境支付的一致性模型，默认就是最终一致 + 补偿。**

#### 编排（Orchestration）vs 编舞（Choreography）

| | 编排 | 编舞 |
|---|---|---|
| 控制流 | 中央协调器显式推进 | 各服务订阅事件自行反应 |
| 可见性 | 流程集中可见 | 流程散落，难追踪 |
| 耦合 | 协调器知道所有参与者 | 参与者只知道自己 |
| 适合场景 | 有明确主流程、需要补偿 | 事件驱动、参与者多变 |

**跨境支付应该选编排**，理由：

1. **补偿逻辑必须有明确归属**。钱已经扣了，退款失败怎么办？需要一个地方统一处理"补偿的补偿"。
2. **监管要求可追溯**。"这笔钱现在在哪一步"必须能回答。编排器的状态就是答案。
3. **不可逆操作需要显式管理**（见下）。

#### 不可逆操作：Saga 理论最大的漏洞

经典 Saga 假设每个步骤都有对应的补偿操作。但在支付里，**有些操作不可逆**：

| 操作 | 可逆？ | 补偿方式 |
|---|---|---|
| 冻结额度 | ✅ | 解冻 |
| 通道扣款 | ⚠️ | 退款（有成本，可能失败） |
| 汇率锁定 | ⚠️ | 撤销锁汇（有汇差损失） |
| 已完成的跨境汇款 | ❌ | **无法撤销**，只能反向汇款 |
| 已申报的外汇 | ❌ | 需要冲正申报，流程复杂 |
| 商户已提现 | ❌ | 只能走法律追偿 |

**这是 Saga 理论在支付领域落地的最大坑。**

应对方式（必须在领域模型中显式表达）：

1. **引入"确认点"概念**：把不可逆操作尽量后置。在"确认点"之前，所有步骤都可补偿。
2. **区分 Try/Confirm 语义**：这其实是 TCC 而非 Saga。资金类操作更适合 TCC——先 Try（冻结），全部成功后再 Confirm（真正执行）。
3. **对不可逆步骤建立"人工介入"通道**：不要试图自动化所有补偿。跨境汇款的差错处理，本质上需要人工。

> **一个务实的判断**：跨境支付的资金链路，应该以 TCC 为主（Try-Confirm-Cancel，冻结/执行/释放），
> 以 Saga 为辅（用于非资金类的编排，如通知、记账、统计）。
> 把两者混用而不加区分，是很多事故的根因。

### 3.4 拒付与争议：国内完全没有的领域

国内支付没有 chargeback 概念。用户不认可交易，走的是"投诉 → 平台介入 → 协商退款"。

跨境卡支付则有一套**由卡组织定义的、有严格时限的**争议流程：

```
持卡人发起争议 → 收单行通知商户 → 商户举证（有时限！）
      → 卡组织裁定 → 可能的二次申辩（representment）→ 终裁
```

#### 领域建模要点

```
Dispute（争议聚合）
  ├── 关联的原始支付（PaymentOrder 的引用，不是包含）
  ├── 争议类型编码（Reason Code，卡组织定义）
  │     ├── 10.x  未收到商品/服务
  │     ├── 13.x  商品与描述不符
  │     ├── 4853  持卡人不认可
  │     ├── 4863  持卡人未授权
  │     └── ...
  ├── 时限（deadline）        ← 核心！超时自动判负
  ├── 举证材料（Evidence）
  └── 状态机
        INQUIRY → CHARGEBACK → REPRESENTMENT → PRE_ARBITRATION
              → ARBITRATION → CLOSED
```

**"时限"是争议域最重要的概念。** 举证窗口通常是 7~30 天（依卡组织和争议类型而定），超时自动判负，资金被强制扣回。

这带来两个建模要求：

1. **时限必须是领域对象的一部分**，而不是散落在定时任务里的魔法数字
2. **时限到期前必须有主动提醒机制**（领域事件 + 定时任务）

#### 争议率：一个必须建模的业务指标

卡组织对商户的争议率有硬性要求（如 Visa 的 VAMP 阈值约 0.9%~1.5%）。超过阈值会进入监控程序，甚至被罚款、停用通道。

这意味着**争议率不是一个报表指标，而是会影响业务可用性的领域概念**：

```
DisputeRate（争议率）
  ├── 统计窗口（滚动 30 天 / 自然月）
  ├── 分子：争议笔数 / 金额
  ├── 分母：交易笔数 / 金额
  ├── 阈值（卡组织 × 商户类别）
  └── 超限动作：告警 / 限流 / 强制 3DS / 停用
```

把这个反馈回路建进领域模型（争议率超限 → 自动提升风控等级），是从"事后处理"走向"主动防御"的关键一步。

### 3.5 时区与日切：被严重低估的复杂度

**"今天"是谁的今天？**

- 中国 UTC+8，日切 23:00（银行）或 00:00
- 美国 UTC-5 ~ UTC-8，日切 ET 时间
- 欧洲 UTC+0 ~ UTC+2，日切 CET
- 部分中东市场周日是工作日

当系统需要回答"今天的交易总额"时，这个问题没有唯一答案。

#### 建模方式

```
SettlementWindow（结算窗口）  —— 值对象
  ├── timezone（时区 ID，如 America/New_York）
  ├── cutoffTime（日切时刻，如 17:00）
  ├── businessCalendar（工作日历，含当地节假日）
  └── 计算给定 Instant 属于哪个结算日
```

**关键设计决策：所有时间以 `Instant`（绝对时间）存储，展示和聚合时按 `SettlementWindow` 转换。**

反模式是存本地时间字符串——跨时区排序、聚合、对账会全线崩溃。

#### 节假日：一个容易漏掉的点

不同市场的节假日完全不同，且**部分市场的节假日是宗教历法**（如斋月、开斋节），每年公历日期不同，需要外部日历服务。

对跨境结算的影响：T+1 结算遇到当地节假日要顺延。这个规则必须在 `SettlementWindow` 里显式处理，否则会出现"承诺 T+1 但实际 T+3"的商户投诉。

## 四、战术设计的落地要点

### 4.1 聚合边界：跨境场景新增的不变量

聚合划分的第一原则是"**在一致性边界内建模真正的不变量**"。跨境场景新增了这些不变量：

| 不变量 | 所属聚合 | 若违反的后果 |
|---|---|---|
| 累计退款 ≤ 原金额 | PaymentOrder | 超额退款，资损 |
| 累计请款 ≤ 授权金额 | Authorization | 多扣用户钱 |
| 累计分账 = 结算金额 | SettlementOrder | 分账差额 |
| 提现额 ≤ 可用余额 - 冻结中 | MerchantBalance | 超额提现 |
| 锁汇在有效期内 | RateLock | 汇率敞口 |
| 争议举证不超时 | Dispute | 自动判负 |

**判定技巧**：如果一个规则需要"读取已有记录 → 校验 → 写入新记录"，且并发下有风险，那它就应该是聚合内的不变量。

### 4.2 值对象：跨境场景的值对象清单

| 值对象 | 为什么是值对象 | 关键设计 |
|---|---|---|
| `Money` | 无身份，靠值相等 | 内部 long + 币种指数，运算要求同币种 |
| `Currency` | 无身份 | 自带指数，避免外部依赖 |
| `ExchangeRate` | 无身份，**但有时效** | 必须含报价时间与失效时间 |
| `BicSwift` / `Iban` / `RoutingNumber` | 无身份 | 自带校验规则与格式化 |
| `SettlementWindow` | 无身份 | 时区 + 日切 + 日历 |
| `CountryCode` / `Region` | 无身份 | 关联合规规则与通道可用性 |
| `MerchantCategoryCode (MCC)` | 无身份 | 影响费率、争议率阈值、风控 |

### 4.3 领域事件：跨境场景的设计要点

**① 事件必须携带"事实的完整上下文"**

消费方不应该为了理解事件再去查一遍。PaymentSucceeded 应该携带金额、币种、汇率、通道、手续费——否则结算上下文消费时还要回调收单上下文查询，形成隐式耦合。

**② 事件必须版本化**

跨境链路上的消费方可能分布在不同团队、不同系统。事件结构变更必须向后兼容。

**③ 事件必须幂等可消费**

Outbox 模式保证"至少一次投递"，消费端必须幂等。这是**必要配套**，不是可选优化。

**④ 关键事件需要"对账级"的完整性**

财务相关的事件（支付成功、退款成功、结算完成）需要保证不丢。实践中通常需要：
- 事件 ID 全局唯一且可追溯
- 关键事件有独立的持久化（不只是 MQ）
- 支持按时间范围重放

### 4.4 领域服务 vs 应用服务 vs 聚合：职责边界

这是最容易混淆的地方。一个实用的判定表：

| 逻辑特征 | 归属 |
|---|---|
| 只依赖聚合内部状态 | **聚合** |
| 需要多个聚合协作 | **领域服务** |
| 需要外部能力（通道/仓储/时钟），但表达的是业务规则 | **领域服务**（外部能力作为参数传入） |
| 需要外部能力，且表达的是流程编排 | **应用服务** |
| 事务、锁、幂等、事件发布 | **应用服务** |

**本工程的 `RefundPolicyService` 是个好例子**：它需要"订单状态 + 通道能力"两个输入，后者不属于聚合。但它不自己去查通道能力——由应用层把能力作为参数传入。这样领域服务保持纯净，可零 mock 测试。

## 五、防腐层：通道适配的 DDD 原理解读

本工程的通道适配层是防腐层的完整实现。这里从 DDD 角度拆解它。

### 5.1 为什么通道适配天然是 ACL

| ACL 的特征 | 通道适配的对应 |
|---|---|
| 隔离外部模型的腐蚀 | 微信的 prepay_id、Stripe 的 client_secret 不进入领域模型 |
| 双向翻译 | PayCommand → 通道报文；通道报文 → NotificationParseResult |
| 提供稳定的内部接口 | `PaymentChannelPort` 不随通道升级而变 |
| 可以逐步替换 | 换通道只需换适配器 |

### 5.2 三层防腐，缺一不可

```
  外部模型（脏）          防腐层                    内部模型（干净）
┌───────────────┐
│ Worldpay XML  │──→ 协议转换（XML 解析）
│ <paymentService>       │
└───────────────┘       ↓
┌───────────────┐   语义翻译（AUTHORISED → AUTHORIZED）
│ 通道状态枚举    │──→       │
└───────────────┘       ↓
┌───────────────┐   能力声明（supportsCancel / refundWindowDays）
│ 通道能力差异    │──→       │
└───────────────┘       ↓
                   ChannelCapability → 上层业务
```

**只做前两层的后果**：上层代码出现 `if (channel == WECHAT)`，因为"能不能撤销"这个信息无处可查。

### 5.3 Apple Pay 案例：抽象错误的代价

这是本工程刻意设计的教学案例。

**错误建模**（Apple Pay 作为通道）：
```
ChannelCode { WECHAT, ALIPAY, STRIPE, WORLDPAY, APPLE_PAY, ... }
```

**代价**：
- Stripe 故障时无法把 Apple Pay 流量切到 Worldpay（因为 Apple Pay "就是"一个通道）
- 退款期限、拒付能力等属性无处安放（它们实际属于底层 PSP）
- 对账时无法回答"这笔 Apple Pay 交易实际由谁清算"

**正确建模**（Apple Pay 作为支付方式，委托给通道）：
```
PaymentMethodType.APPLE_PAY  ×  ChannelCode.STRIPE   → 能力矩阵
PaymentMethodType.APPLE_PAY  ×  ChannelCode.WORLDPAY → 能力矩阵
```

**收益**：
- 容灾：切换委托目标即可
- 能力自动正确：继承自 delegate
- 对账清晰：channelCode 返回 delegate 的编码

**这个案例的通用教训**：

> 当我们发现某个"东西"的能力全部来自另一个"东西"时，
> 它大概率不是一个独立实体，而是一个**关系**或**属性**。
> 建模时把它错误地提升为独立实体，会失去整个维度的灵活性。

## 六、常见反模式与误区

### 6.1 把 DDD 做成"分包规范"

**症状**：目录里有 `domain/`、`service/`、`repository/`，但 `domain` 里全是只有 getter/setter 的 PO。

**本质**：这是三层架构换了个包名，不是 DDD。判断标准很简单——**领域对象里有没有业务规则**。

**自检问题**：
- 能不能在不起 Spring、不连数据库的情况下，单测"累计退款不能超额"这条规则？
- 如果不能，说明业务逻辑不在领域层。

### 6.2 聚合设计的两个极端

| 极端 | 症状 | 后果 |
|---|---|---|
| **聚合过大** | PaymentOrder 里塞了商户信息、通道配置、风控结果 | 加载成本高，并发冲突频繁，任何修改都要锁整个聚合 |
| **聚合过小** | 退款独立成聚合 | 无法保证强一致的不变量，产生资损 |

**判定方法**：问"这个规则如果并发执行会出问题吗？" 会 → 放同一聚合。

### 6.3 领域层泄漏框架

**症状**：实体上挂着 `@Entity`、`@Table`、`@Column`；聚合里注入 `@Autowired` 的 Service。

**代价**：
- 领域模型无法独立测试（必须起容器、连数据库）
- 持久化细节影响领域设计（为了 JPA 的懒加载把聚合拆散）
- 框架升级波及业务代码

**本工程的做法**：domain 与 channel-adapter 模块**零外部依赖**（只有 JDK）。这不是洁癖，是为了让领域模型能被独立验证。

### 6.4 事件滥用：把领域事件当成消息通道

**症状**：任何状态变化都发事件，事件膨胀到几百种，消费方互相依赖形成隐式调用链。

**区分标准**：
- **领域事件**：领域中已发生的事实，其他上下文可能关心（PaymentSucceeded）
- **内部状态变更**：实现细节，不应暴露（PaymentAttemptStatusChanged）

**自检**：如果删除所有消费者，这个事件还有意义吗？没有 → 它不是领域事件。

### 6.5 过度抽象：为不存在的通道做抽象

**症状**：为了"统一"设计了一个能容纳所有未来通道的接口，结果每个现有通道都要实现一堆用不到的方法。

**判定**：**抽象应该从三个具体实现中提取，而不是从想象中设计。**

本工程有 9 个通道——足够提取出可信的抽象。如果只有 2 个通道，强行抽象往往是过度设计。

### 6.6 防腐层只做字段映射

已在 5.2 详述。这是通道适配最常见的失败模式：协议转换做得很好，但能力没有建模，导致上层堆满 `if (channel == X)`。

## 七、落地建议

### 7.1 起步顺序

```
第一步：识别核心域              ← 决定资源投放
    ↓
第二步：画上下文映射图           ← 决定集成模式与团队边界
    ↓
第三步：在核心域内做战术设计      ← 聚合、值对象、事件
    ↓
第四步：支撑域用最简单的方式实现  ← 不要在这里炫技
```

**不要在支撑域上花时间做精致建模。** 对账、通知、统计这些，代码能跑、逻辑清晰就够了。

### 7.2 团队组织与上下文的对应（康威定律）

限界上下文应该是**团队边界**的依据。一个上下文一个团队，团队内部可以自由修改，跨团队通过事件契约协作。

如果上下文边界与团队边界不一致，会出现：
- 两个人同时改一个聚合，互相冲突
- 一个改动需要跨三个团队评审，迭代速度归零

### 7.3 演进式建模

**不要试图一次设计出完美的领域模型。**

领域模型应该随认知深入而演进。本工程中就有活生生的例子：

- 初版 `requestRefund` 把 `expireAt != null` 作为退款期限校验的前置条件——这是个顺手加的错误条件，导致未设过期时间的订单永久跳过期限校验。它在测试全绿的情况下存活，直到构造"200 天前的订单"这个用例才暴露。
- 初版 `reconstitute` 没有回填 `createdAt`，导致从数据库重建的历史订单，创建时间被替换成当前时间，所有依赖账龄的校验失效。

**这两个缺陷的共同点**：它们都不会导致功能"看起来不正常"，只会在特定业务场景下静默地产生错误结果。这正是领域建模需要持续投入的原因——**错误的概念比错误的代码更隐蔽，也更昂贵**。

### 7.4 一份自检清单

模型是否健康，用这几个问题检验：

| # | 问题 | 期望答案 |
|---|---|---|
| 1 | 能否不起容器、不连 DB 单测核心业务规则？ | 能 |
| 2 | 新增一个通道，需要改几处业务代码？ | 0 处（只加适配器） |
| 3 | 能否回答"这笔钱现在在哪一步"？ | 能（编排器状态 + 事件流） |
| 4 | 并发退款会不会超额？ | 不会（聚合不变量 + 锁） |
| 5 | 通道回调乱序会不会导致状态回退？ | 不会（状态机终态守卫） |
| 6 | 某市场新增一条合规要求，影响范围？ | 仅合规上下文 |
| 7 | 领域里有没有 `@Entity` / `@Autowired`？ | 没有 |
| 8 | 能否说清哪些是核心域？ | 能，且与团队资源投放一致 |

---

## 八、结论

1. **跨境支付的复杂度是有结构的**，主要分为五个深水区：多币种与汇率、合规、长事务、争议、时区日切。这五个在国内支付中要么不存在，要么极度弱化。

2. **DDD 在跨境支付上的最大价值在战略设计**，尤其是核心域判定与上下文映射。战术设计（聚合、值对象）重要但相对标准化。

3. **防腐层必须用足三层**：协议转换、语义翻译、**能力声明**。只做前两层会让上层退化成 if-else。

4. **Apple Pay 案例的通用教训**：当某物的能力全部来自另一物时，它是关系而非实体。错把它建模成实体，会失去整个维度的灵活性。

5. **不可逆操作是 Saga 理论在支付领域的最大漏洞**。资金链路应以 TCC 为主、Saga 为辅，并为不可逆步骤保留人工介入通道。

6. **不要神化 DDD**。它解决不了定价策略、通道谈判、牌照获取。把 DDD 当工具，不当宗教。

7. **领域模型会出错，而且错误很隐蔽**。两个真实缺陷（退款期限的前置条件、重建时的时间回填）都在测试全绿的情况下存活——错误的概念比错误的代码更昂贵，因为代码错误会崩溃，概念错误只会静默地产生错误的钱。
