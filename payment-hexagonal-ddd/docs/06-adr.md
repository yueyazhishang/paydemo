# 06 关键设计决策（ADR）

> ADR = Architecture Decision Record。记录每个取舍的**理由**和**被否决的方案**。
> 只写结论的文档三个月后就没人看得懂了，能看懂的是「当时为什么这么选」。

---

## ADR-001：用能力矩阵表达通道差异，而不是 if-else

**状态**：已采纳

**背景**：九家通道的能力差异极大（是否支持授权分离、部分退款次数、退款窗口、幂等维度……）。朴素做法是在业务代码里 `if (channel == WECHAT)`。

**决策**：把差异建模成 `ChannelCapability` 数据，业务代码只问 `capability.supports(XXX)`。

**理由**：

| | if-else | 能力矩阵 |
|---|---|---|
| 新增通道 | 改 N 处业务代码 | 加一份配置 + 一个适配器 |
| 调用方能否预知支持情况 | 不能，运行时炸 | 能，编译期即可查 |
| 排除原因是否可观测 | 否 | 是（`missingCapabilities()` 返回缺失项） |
| 降级切换是否有依据 | 无 | 有（`covers()` 校验能力对等） |

**被否决的方案**：策略模式（每家通道一个 `PaymentStrategy`）。问题在于**能力的组合爆炸** —— 退款窗口、次数、部分退款、幂等维度这些是正交的，用策略类表达会需要几十个方法，且无法做「能力对等」的降级判断。

**代价**：能力配置本身有维护成本，通道新增能力时要同步更新配置。为此 `CapabilityMatcher` 在匹配失败时返回**具体缺失项**而非布尔值，方便快速定位配置遗漏。

## ADR-002：一个能力一个端口，而不是万能网关接口

**状态**：已采纳

**决策**：拆成 `ChannelPaymentPort` / `ChannelQueryPort` / `ChannelCapturePort` / `ChannelVoidPort` / `ChannelReversePort` / `ChannelClosePort` / `ChannelRefundPort` / `ChannelRefundQueryPort`，适配器只实现自己真正具备的。

**理由**：万能接口迫使不支持的方法实现成 `throw new UnsupportedOperationException()`，导致：
1. 调用方**编译期**无法知道某通道是否支持某能力
2. 代码里再也分不清「真的不支持」和「还没实现」

**被否决的方案**：单个 `ChannelGateway` 接口。见上。

**实际效果**：微信的适配器里**看不到** `capture` / `voidAuthorization` 方法 —— 微信是 SALE 模型，没有这两个能力。调用方若要对微信发起请款，连编译都过不了。

## ADR-003：`PaymentAttempt` 在聚合内，`RefundOrder` 在聚合外

**状态**：已采纳

**决策**：支付尝试作为 `PaymentOrder` 的内部实体；退款单作为独立聚合根。

**理由**：

| | 判断依据 | 结论 |
|---|---|---|
| `PaymentAttempt` | 存在跨尝试的强不变量：同一时刻同通道只能有一个进行中的尝试 | 必须同事务 → **聚合内** |
| `RefundOrder` | 只需「累计退款不超额」，靠一个数值字段 + 乐观锁即可 | 无跨聚合不变量 → **独立聚合** |

**被否决的方案**：把退款单内嵌进支付单。后果：支付单随退款次数线性膨胀，每次退款都要加载整个聚合，并发的部分退款在聚合锁上串行化 —— **收益为零，代价很大**。

**判断原则**：按不变量划边界，不按「看起来像父子关系」划边界。「退款属于支付」是从属关系，不是不变量关系。

## ADR-004：幂等键确定性生成，不用 UUID

**状态**：已采纳

**决策**：`IdempotencyKeyFactory.channelPaymentKey(orderId, channel)` —— 由业务标识推导。

**理由**：生成 key、持久化、调用通道三步不是原子的。用随机 key，进程崩溃后重试必然产生第二笔交易。

**被否决的方案**：
- UUID / 随机数 —— 崩溃即丢失
- `hashCode()` —— JDK 版本间不保证稳定，碰撞概率高。**碰撞 = 两笔交易共用一个幂等键，其中一笔被静默吞掉**

**细节**：请款键要带序号（`cap:PAY001:2`），因为一笔授权可能分多次部分请款。

## ADR-005：超时按「结果未知」处理，绝不判失败

**状态**：已采纳

**决策**：适配器遇到超时返回 `FailureInfo.unknown(...)`；聚合根收到后保持中间态，返回 `UNKNOWN_NEEDS_QUERY`。

**理由**：调用通道超时，不代表用户没被扣款 —— 很可能通道已经扣款成功，只是响应没回到我们这里。直接判失败会造成**「用户付了钱，订单是失败的」**，这是支付系统最严重的事故类型之一。

**被否决的方案**：超时即置 `FAILED`。后果见上。

**配套措施**：补偿任务持续扫描中间态订单，主动查单推进状态。

## ADR-006：归一化状态与通道原始状态双轨保留

**状态**：已采纳

**决策**：`ChannelRawStatus` 同时保存 `rawStatus`（通道原始字符串）与 `normalized`（归一化状态），一并持久化。

**理由**：归一化是有损压缩。

- 支付宝 `TRADE_SUCCESS`（可退款）与 `TRADE_FINISHED`（**不可退款**）归一化后都是 `SUCCEEDED`。只看归一化状态发起退款，会对一笔注定失败的请求白跑一趟。
- 微信 `PAYERROR` 可能是余额不足，也可能是风控拦截，运营处理截然不同。
- 通道新增状态时，可以先落到最接近的归一化状态，原始值仍在，不会形成数据黑洞。

**被否决的方案**：只存归一化状态。丢失的信息在对账和客服环节无法找回。

## ADR-007：状态机集中管理，终态不可逆

**状态**：已采纳

**决策**：所有合法转移集中在 `PaymentStateMachine` 的一张表里。

**理由**：
1. 可审计 —— 一张表看完所有规则
2. 天然防御乱序通知 —— 非法转移直接被拒
3. 终态不可逆 —— 杜绝「用户已付款、订单却被关掉」

**关键约束**：`SUCCEEDED → CLOSED` **不在合法转移表中**。已支付的订单要终止必须走退款，否则形成账务黑洞。

**细节**：`from == to` 视为合法（幂等）。通道重复投递同一条通知时不应报错。

## ADR-008：回调处理返回结果枚举，不抛异常

**状态**：已采纳

**决策**：`applyChannelResult` 返回 `ChannelResultApplication` 枚举，而不是抛异常。

**理由**：回调接口返回 5xx，通道会按重试策略反复推送（微信 15 次），同一笔问题被放大十几次，告警淹没一切，而问题本身一点没解决。

**被否决的方案**：处理失败抛异常 → 接口返回 500 → 通道重试。

**配套**：`TERMINAL_CONFLICT_PAID_AFTER_CLOSE` 专门标记「订单已关闭但用户已付款」，必须触发自动退款。

## ADR-009：领域事件在事务提交后发布

**状态**：已采纳（本工程简化为同步发布）

**决策**：应用层在 `save` 之后调用 `eventPublisher.publishAll(...)`，然后 `clearDomainEvents()`。

**理由**：先发消息、后提交事务，一旦事务回滚，消息已经出去了。下游的清结算、商户通知、发货系统全都认为「支付成功」，而库里根本没有这笔 —— 经典的**幽灵消息**问题，事后极难清理。

**被否决的方案**：在聚合根的方法里直接发消息。这会绕过事务边界。

**本工程的简化**：`LoggingDomainEventPublisher` 是同步的，进程崩溃会丢事件。

**生产必须改成事务性发件箱（Transactional Outbox）**：事件与业务数据同库同事务写入 `outbox` 表，由独立的投递任务读取发送。这样「业务数据存在」与「事件一定会被发出」是原子的。

## ADR-010：仓储不得清空领域事件

**状态**：已采纳

**决策**：`PaymentOrderRepository.save()` 只做持久化与乐观锁校验，**不调用** `clearDomainEvents()`。

**理由**：事件的生命周期归应用层管 —— 「落库 → 发布 → 清理」。仓储若提前清空，事件就永远发不出去了。

**这个坑有多容易踩**：把 `clearDomainEvents()` 写在 `save()` 里看起来很自然（「保存完了就清理」），但它是错的。本工程在初次实现时犯了这个错，靠 review 才发现。

## ADR-011：装配根放在 interfaces，用 Maven 作用域约束依赖方向

**状态**：已采纳（对纯六边形的一处妥协）

**决策**：`infrastructure` 在 `interfaces` 的 pom 里是 `runtime` 作用域；启动类 `@SpringBootApplication(scanBasePackages = "com.zxpay")`。

**理由**：
- 标准六边形会把装配根单独拆成 `boot` 模块。这里为了少一层目录而合并。
- 但用 `runtime` 作用域在**构建层面**兜住了依赖方向：入站适配器想 `new WeChatPayAdapter()`，编译都过不了。
- 用构建工具表达架构约束，比靠 Code Review 提醒有效得多。

**被否决的方案**：
- 拆 `boot` 模块 —— 更标准，但目录多一层，对教学工程是负担
- `compile` 作用域 —— 约束失效

## ADR-012：金额用 Money 值对象，币种自带小数位

**状态**：已采纳

**决策**：`Money` 不可变，精度由 `Currency.minorUnits()` 决定，跨币种运算抛异常。

**理由**：

| 币种 | 小数位 | 统一按 2 位的后果 |
|---|---|---|
| CNY / USD / EUR | 2 | 正确 |
| **JPY / KRW / VND** | **0** | **金额被放大 100 倍** |
| **BHD / KWD** | **3** | **金额被缩小 10 倍** |

零小数位币种是跨境支付的经典事故源。因此**业务代码里严禁出现 `amount * 100`**，一律走 `Money.minorUnits()` / `Money.ofMinor()`。

**被否决的方案**：统一按 2 位小数处理。见上表。

## ADR-013：适配器用模板方法模式，通道差异下沉为配置

**状态**：已采纳

**决策**：`AbstractChannelAdapter` 固定「下单 → 拿结果 → 翻译」的骨架，九个子类只声明状态名、唤起参数形态、错误码。

**理由**：九家适配器的流程 90% 相同。若各家写一个完整类，改一处流程要改九遍。

**模拟策略的额外收益**：`simulateById(attemptId)` 按 attemptId 哈希做**确定性**模拟。同一个 attemptId 永远得到同一个结果 —— 这让「重试」这件事可以被真正验证：重试时 attemptId 不变，结果不变，不会因为随机性掩盖幂等缺陷。

## ADR-014：路由把健康度算进打分

**状态**：已采纳

**决策**：`ChannelRoutingService.score()` 综合基础优先级、成功率、耗时、熔断状态、费率。

**理由**：只按费率选，会永远把流量打向最便宜的通道。当该通道开始抖动时，流量不会自动撤离，失败率雪崩。

```java
score += (1.0d - health.successRate()) * 200.0d;      // 完全失败的通道 +200
if (health.shouldBeIsolated(FAILURE_ISOLATION_THRESHOLD)) {
    score += 500.0d;                                  // 熔断通道几乎排除
}
score += contract.feeRateBps() / 10.0d;               // 成本：千六 = 6 分
```

**演示数据**：`InMemoryChannelHealthQuery` 里 Worldpay 的连续失败 12 次且已降级 —— 即便它费率最低（250 bps），也会因健康度惩罚被排到后面。

**打分公式刻意保持简单可读**。生产里通常是可配置的权重表，甚至接在线学习模型，但**结构不变**：把「打分」独立成一个可替换的策略。

## ADR-015：路由三层过滤的顺序不能变

**状态**：已采纳

**决策**：签约过滤 → 能力过滤 → 打分排序。

**理由**：签约过滤必须在能力匹配**之前**。否则会选出一家「能力满足但没签约」的通道，下单时才报「商户号不存在」。

```java
// 第一层：签约过滤
List<ChannelContract> signed = app.contractsFor(instruction.paymentMethod());
if (signed.isEmpty()) {
    return RoutingDecision.noChannel("no signed channel for payment method ...");
}
// 第二层：能力过滤
CapabilityMatcher.MatchResult match = CapabilityMatcher.match(capability, requirement);
// 第三层：打分
candidates.add(score(capability, contract));
```

## 附：本工程已知的教学简化

| 简化 | 生产应该怎么做 |
|---|---|
| 通道调用是确定性模拟 | 真实 HTTPS + 签名 + 超时 + 解密敏感字段 |
| 持久化用内存 Map | MySQL 分库分表 + 乐观锁 + 联合索引 |
| 事件发布是同步打印 | **事务性发件箱（Transactional Outbox）** |
| 幂等存储用内存 Map | Redis + `SETNX` 原子占用 |
| 分布式锁用内存 Map | Redis 或数据库锁 |
| 没有结算上下文 | 结算批次、手续费、对账、差错处理 |
| 没有对账与差错处理 | 通道账单解析、长短款、差错工单 |
| 没有风控上下文 | 实时决策、规则引擎、名单库 |
| `settled` 标志固定为 false | 查询交易是否已进入结算批次 |
